## อ่านผลอย่างไร

### 1. D-FINE คือของจริง — ล้ม rtdetr-l ได้ชัดเจน

`dfine-n` **แม่นเท่า `rtdetr-l` (ถูกบัง 97% ทั้งคู่) แต่เร็วกว่า 2.3 เท่า**
และ recall รวมยังดีกว่าด้วย (92% vs 90%) แปลว่าข้อสรุปเดิมที่ว่า
"transformer detector ไม่คุ้ม" มาจากการวัด `rtdetr-l` ซึ่งเป็นรุ่นใหญ่สุด —
ไม่ใช่ข้อจำกัดของสถาปัตยกรรม

เทียบกับ baseline: `dfine-n` แม่นกว่า `yolo11s` 3 จุด (97% vs 94%) โดยจ่าย
compute 2 เท่า ส่วน `dfine-m` **จับคนถูกบังได้ครบ 69/69 = 100%**

### 2. แต่ยังไม่ควรเปลี่ยน production ทันที

`dfine-n` ที่ 434 ms ยังช้ากว่า `yolo11s` ที่ 217 ms **สองเท่า** และตัวเลขนี้เป็น
PyTorch ล้วน ยังไม่ได้ export OpenVINO เหมือนที่ทำกับ YOLO ไว้แล้ว

ถ้า D-FINE ได้อัตราเร่งแบบเดียวกับที่ YOLO ได้ (1.7-2.6 เท่า) `dfine-n` จะลงมา
อยู่ ~170-255 ms ที่ recall คนถูกบัง 97% = **ชนะ `yolo11s` ทั้งความเร็วและความแม่น**
นี่คือการทดลองถัดไปที่คุ้มที่สุด (ดู `context.md` ข้อ 13)

อีกข้อที่ต้องดู: false positive ของ D-FINE สูงกว่า (4-7 vs 2) สำหรับงาน occupancy
FP แปลเป็น "แจ้ง PRESENT ตอนไม่มีคน" ซึ่งแย่กว่า recall ที่หายไป — ต้องจูน `conf`
ขึ้นก่อนใช้จริง

### 3. RTMDet แพ้ขาด — ตัดทิ้งได้

`rtmdet-tiny` (265 ms / ถูกบัง 83%) **ทั้งช้ากว่าและแม่นน้อยกว่า** `yolo11n`
(141 ms / 88%) ส่วน `rtmdet-s` ก็แพ้ `yolo11s` ในทุกช่อง ไม่มีเหตุผลให้ใช้

### 4. `rtmdet-n-person` — 23 ms เร็วกว่าทุกตัว 9 เท่า

recall ต่ำ (53%/64%) แต่ **false positive = 0** และเร็วกว่า `yolo11s` **9.4 เท่า**
input แค่ 320x320 คลาสเดียว

⚠️ ตัวนี้เข้าข่ายเดียวกับ OpenVINO person-detection ที่วัดไว้ก่อนหน้า — **เทรนกับ
ภาพกล้องวงจรปิดมองลงมา แต่ถูกทดสอบด้วยภาพ COCO ระดับสายตา** การวัดนี้ลำเอียง
ต่อต้านมัน ที่ 23 ms มันเป็นตัวเดียวที่รันได้หลายสิบกล้องบน edge box ตัวเดียว
**ต้องวัดซ้ำด้วยภาพจากกล้องที่ติดจริงก่อนตัดสิน**

### 5. CrowdHuman fine-tune ล้มเหลว — สมมติฐานผิด

คาดว่าน้ำหนักที่เทรนบน CrowdHuman (ฉากแออัด/ถูกบัง) จะชนะเรื่องคนถูกบัง
**ผลออกมาตรงข้าม: 63%/75% แย่กว่า `yolov8n` เปล่าๆ (75%/81%) ทุกช่อง
และ false positive มากกว่า**

สาเหตุที่น่าจะเป็น — ไม่ใช่ข้อสรุปว่า CrowdHuman ใช้ไม่ได้:

- checkpoint ที่ใช้เป็น `best.pt` จาก training run ของคนทั่วไปบน HF ไม่ใช่
  reference weights ที่มีตัวเลขยืนยัน คุณภาพการเทรนไม่ทราบ
- CrowdHuman เทรนคลาสเดียวบน dataset แคบ → เสีย generality ที่ COCO ให้
- นิยามกล่องต่างกัน: CrowdHuman ใช้ **full-body** (รวมส่วนที่ถูกบัง) ส่วน COCO
  ใช้ขอบเขตที่มองเห็น ทำให้ center ที่คำนวณได้เลื่อนจาก GT ของ COCO

ถ้าจะเอาแนวคิด CrowdHuman จริง ต้อง fine-tune เองจาก dataset ต้นฉบับ ไม่ใช่
หยิบ checkpoint จาก hub


> ms รอบนี้ต่ำกว่ารอบที่ 2 ราว **2.2 เท่าทุกแถว** (yolo11s 97.0 vs 217.3) เพราะ
> เครื่องเย็นกว่า ไม่ใช่ว่าอะไรเร็วขึ้น — เทียบภายในตารางนี้เท่านั้น

## อ่านผลอย่างไร

### 1. สมมติฐานถูก — OpenVINO เร่ง D-FINE ได้มากกว่าที่เร่ง YOLO

| | pytorch | openvino | เร่งได้ |
|---|---|---|---|
| dfine-n | 163.2 | 55.0 | **2.97x** |
| yolo11s | 97.0 | 40.4 | 2.40x |

ผลคือ `dfine-n` + OpenVINO **เร็วกว่า `yolo11s` pytorch 1.76 เท่า และแม่นกว่า**
(ถูกบัง 97% vs 94%, recall รวม 92% vs 85%) — ได้ทั้งสองอย่างโดยไม่ต้องแลก
ตรงกับที่คาดไว้ในรอบที่ 2 ว่าจะลงมาอยู่ ~170-255 ms (ได้จริง = 0.57x ของ yolo11s)

**recall ตรงกับ PyTorch เป๊ะทุกช่อง** (120/131, 67/69, FP 4) ยืนยันว่าการแปลงไม่
ทำให้ผลเปลี่ยน — ต่างจาก YOLO ที่ export แล้วตกเล็กน้อย (94% → 93%)

### 2. INT8 ได้ผลน้อยกว่าที่คาด — ผมประมาณไว้ผิด

ในรอบที่ 2 เขียนไว้ว่า INT8 "ปกติได้อีก 2-3 เท่าบน CPU Intel" **ผลจริงได้แค่ 1.22 เท่า**
(55.0 → 45.0 ms)

เหตุผล: NNCF ต้องรับ `model_type=nncf.ModelType.TRANSFORMER` ซึ่งกัน attention/
softmax ไม่ให้ quantize (ถ้าไม่กัน ความแม่นตกหนัก) จึงเหลือส่วนที่เป็น INT8 จริง
น้อยกว่าโมเดล CNN ที่ตัวเลข "2-3 เท่า" มาจาก

ราคาที่จ่าย: recall รวม 92% → 89%, **FP 4 → 6** (ถูกบังยัง 97% เท่าเดิม)
กำไรที่ได้จริงคือ**ขนาดโมเดล 15.9 → 5.4 MB** ซึ่งมีค่ากับ edge box พื้นที่จำกัด
แต่ไม่ใช่การเร่งความเร็ว

### 3. ตัวเลือกกลายเป็น 3 ทาง — และ FP เป็นตัวตัดสิน

| ตัวเลือก | × yolo11s | ถูกบัง | FP |
|---|---|---|---|
| `yolo11s` + OpenVINO | 0.42x | 93% | 2 |
| `dfine-n` + OV INT8 | 0.46x | **97%** | 6 |
| `dfine-n` + OpenVINO | 0.57x | **97%** | 4 |

FP สำคัญกับงานนี้เป็นพิเศษเพราะแปลเป็น **"รายงาน PRESENT ตอนไม่มีคน"** ซึ่งผิด
ในทิศที่แย่กว่าการพลาดคน (คนที่นั่งอยู่จะถูกจับได้ในเฟรมถัดไปอยู่ดี ที่ 2 fps)

**ยังไม่เปลี่ยน production** — ต้องจูน `conf` ขึ้นจาก 0.5 แล้ววัด FP ซ้ำก่อน
และ `desk_occupancy_multi.py` ยังโหลดโมเดลผ่าน `ultralytics` เท่านั้น
ต้องเพิ่ม backend ฝั่ง production ด้วย (ดู `context.md` ข้อ 14)

## ความเชื่อถือได้ของตัวเลข

รันชุดนี้ **3 ครั้ง** ในช่วงเวลาต่างกัน — **recall กับ FP ออกมาตรงกันเป๊ะทุกแถวทุกครั้ง**
ส่วน ms แกว่ง และอัตราส่วนแกว่งราว 3%:

| | ครั้งที่ 1 | ครั้งที่ 2 (เก็บไว้) |
|---|---|---|
| dfine-n → ov เร่งได้ | 3.06x | **2.97x** |
| yolo11s → ov เร่งได้ | 2.51x | **2.40x** |
| dfine-n-ov vs yolo11s pt | 1.79x | **1.76x** |
| INT8 vs FP32 | 1.23x | **1.22x** |

ตัวเลขในเอกสารนี้ใช้ครั้งที่ 2 ซึ่งเก็บถาวรไว้ที่
`benchmark/results/2026-09-16_1335.json` (ตั้งแต่รอบนี้ไป ทุกการรันจะเก็บสำเนา
ลง `benchmark/results/` ไม่ทับกัน — `results_latest.json` เป็นตัวชี้รอบล่าสุด)

## บทเรียนที่ใช้ซ้ำได้

**อย่าเทียบโมเดลข้ามรูปแบบ runtime** — ในรอบที่ 2 `dfine-n` ดู "ช้ากว่า `yolo11s`
2 เท่า" ซึ่งเป็นการเทียบ pytorch กับ pytorch พอ export ทั้งคู่เป็น OpenVINO

ถ้าตัดสินใจจากรอบที่ 2 อย่างเดียวจะทิ้งตัวที่ดีกว่าไปเลย

## สิ่งที่รอบนี้บอกและรอบก่อนบอกไม่ได้

**recall ไม่ใช่ตัวแยกโมเดลอีกต่อไป** — บนฉากโต๊ะจริงทุกตัวหลักได้ 92-100%
(ชุดเดิมกระจาย 76-92%) เพราะคนนั่งหน้าจอเป็นคนตัวใหญ่ในเฟรม
**ตัวที่แยกแพ้ชนะคือ false positive** ซึ่งต่างกันถึง 9 เท่า (1 vs 9)

**และ `dfine-n` แพ้ตรงนั้นพอดี** — เด้ง PRESENT บนโต๊ะว่าง 3/31 ใบ ส่วน

ขึ้น conf มีแต่เสีย recall

## ยังไม่เปลี่ยน production

`yolo11n` + conf 0.5 (ค่าปัจจุบันใน `occupancy.yaml`) ออกมาเป็นตัวที่ปลอดภัยที่สุด
เรื่อง false PRESENT บนชุดนี้อยู่แล้ว การสลับไป D-FINE แลก FP สูงกว่า 4 เท่า
เพื่อ recall +8 จุด ซึ่งบนชุด n=25 **ยังไม่ใช่หลักฐานพอ**

## สองเรื่องที่ต้องเปิดภาพดูถึงจะรู้

**FP พุ่งเป็น 66-138 (ชุด COCO ได้ 1-14)** — เปิดดู FP ของ `yolo11n` ทั้ง 66 จุด
เกือบทั้งหมดตกบน**คนจริงที่ไม่มีกล่อง GT** มีภาพที่คน 3 คนแต่ label ไว้คนเดียว
ทั้งที่ 397 จาก 400 ภาพมี image-level label ยืนยันว่ามีคนแล้ว
→ **Open Images ไม่ได้ annotate คนครบทุกคน** คอลัมน์ FP ของชุดนี้ใช้ไม่ได้

**ภาพโต๊ะว่าง 95 ใบที่สร้างไว้ มีคนอยู่จริง** — ตอนแรกถือว่า image-level label
ที่คลาส Person มี `Confidence=0` แปลว่า "ยืนยันว่าไม่มีคน" ผลวัดออกมาทุกโมเดล
พลาด 17-23 ใบ **เท่าๆ กันหมด** แม้แต่ `rtmdet-n-person` ที่ได้ 0/31 บนชุด COCO
ซึ่งผิดปกติเกินกว่าจะเป็นเรื่องของโมเดล เปิดดู 17 ใบที่มันเด้ง — เด็กสองคน
หน้าแล็ปท็อป มือพิมพ์คีย์บอร์ด คนยืนข้างเปียโน **มีคนจริงแทบทุกใบ**
`Confidence=0` แปลว่า "ผู้ตรวจตอบว่าป้ายนี้ไม่ตรง" ไม่ใช่ "ในภาพไม่มีคน"
→ ตัดภาพ negative ทิ้งทั้งหมด และให้ harness ขึ้นคำเตือนเองทุกครั้งที่รันชุดนี้

## dataset ที่ลองแล้วใช้ไม่ได้

`bdanko/overhead-person-detection` (13,448 ภาพ) และ `bdanko/overhead-people-rgb`

ไม่ใช่ทั้งตัว** และ annotate ไม่ครบ วิธีวัดของเราเช็ค center ของ detection
ว่าตกในกล่อง GT ไหม — center ของกล่องเต็มตัวจะตกนอกกล่องหัวเสมอ

## บทเรียนที่ใช้ซ้ำได้

**เกณฑ์คัดลอกข้าม dataset ไม่ได้ถ้าความครบของ annotation ต่างกัน** — เกณฑ์
"ต้องมีเก้าอี้หรือโต๊ะในภาพ" ที่ทำงานดีกับ COCO พอย้ายมา Open Images
ตัดทิ้ง **459 คนจาก 522** เพราะภาพโต๊ะทำงานจำนวนมากไม่มีกล่อง `Desk`/`Chair`
ทั้งที่เห็นโต๊ะเต็มตา

เกณฑ์แบบ **"ต้องมี label X"** ใช้ได้เฉพาะ dataset ที่ annotate ครบทุกคลาสทุกภาพ
ส่วนเกณฑ์แบบ **"ถ้าเจอ label X ให้ตัด"** ปลอดภัยกับทุกชุด

**ตัวเลขที่ผิดปกติแบบเท่ากันทุกโมเดล มักเป็นปัญหาของ ground truth ไม่ใช่ของโมเดล**
— "ทุกโมเดลพลาดโต๊ะว่าง 17-23 ใบ" คือเบาะแสที่ทำให้ไปเปิดภาพดูแล้วเจอว่า GT ผิด
