# โครงการ: ระบบตรวจวัดการเข้าใช้โต๊ะทำงานด้วย CCTV (Desk Occupancy Monitor)

เอกสารนี้ครอบคลุมทั้งโปรเจกต์ — บริบท, การตัดสินใจด้านสถาปัตยกรรม, วิธีติดตั้ง/รัน,
คู่มือการตั้งค่าโซน, ข้อจำกัด และข้อควรระวังด้านกฎหมาย (PDPA)

เป็น **single source of truth** สำหรับนำไปต่อยอดหรือ deploy จริง

## 2. การปรับเป้าหมาย (สำคัญ)

ระบบนี้วัด **สถานะการเข้าใช้โต๊ะ (occupancy/activity)** ไม่ใช่ "ประสิทธิภาพการทำงาน"
CCTV พิสูจน์ไม่ได้ว่าพนักงาน "กำลังทำงานจริง" เพราะคนนั่งนิ่งอาจกำลังคิด/อ่าน/คุยโทรศัพท์

MVP จึงตรวจจับเฉพาะ**สถานะเชิงวัตถุวิสัย (objective)** ที่วัดได้จริง:

| สถานะ | ความหมาย | เงื่อนไข |
|---|---|---|
| `PRESENT` | มีคนที่โต๊ะ | พบ person center ภายใน ROI ของโซน |
| `AWAY` | ไม่มีคนที่โต๊ะ | ไม่พบ person ≥ `away_seconds` |

> **หมายเหตุ:** เวอร์ชันเต็ม (`desk_activity_monitor.py`, `desk_multi_monitor.py` ใน `PLAN.md`)
> มีสถานะ `ACTIVE`/`IDLE`/`AWAY` เพิ่ม แต่เนื่องจาก "นิ่ง ≠ ไม่ทำงาน"
> เวอร์ชัน production จึงใช้ `PRESENT`/`AWAY` ตามที่ผู้ใช้ยืนยันว่า "แค่อยากรู้ว่าเขาทำงานอยู่มั้ย"

## 3. สถาปัตยกรรม

```
[CCTV กล้อง/โต๊ะ] ──RTSP──▶ [Edge Box (ประมวลผลใกล้กล้อง)]
                                  ├── YOLOv8n: ตรวจจับบุคคลบนเต็มเฟรม
                                  ├── แมป person center → โซน (ROI)
                                  ├── State machine: PRESENT / AWAY ต่อโซน
                                  └── เก็บเฉพาะ event log (CSV/SQLite) ไม่เก็บวิดีโอดิบ
                                          │
                                          ▼
                              [Dashboard + หน้าตั้งค่าโซน]  (Flask, port 8080)
```

### Privacy by Design

- ประมวลผลที่ edge box ไม่ส่งวิดีโอดิบขึ้น cloud
- ไม่ทำ face recognition, ไม่ระบุตัวบุคคล, ไม่วิเคราะห์อารมณ์
- เก็บเฉพาะ log การเปลี่ยนสถานะ ไม่ใช่เฟรมภาพ
- รายงานระดับโซน/โต๊ะ ไม่ใช่รายบุคคล
- ตั้งกล้องครอบคลุมโซนโต๊ะ + privacy masking บริเวณที่ไม่จำเป็น

## 4. เทคโนโลยีและการตัดสินใจเลือกใช้

| ส่วน | เทคโนโลยี | เหตุผล |
|---|---|---|
| ตรวจจับบุคคล | **YOLOv8n** (หลัก) | แม่นยำกับคนหลายคน/มุมมองจากด้านบน ตรวจได้ครบ |
| Fallback | MediaPipe Pose → HOG | กรณีไม่มี `ultralytics` |
| วิดีโอ I/O | OpenCV (`opencv-python-headless`) | อ่าน RTSP/webcam/ไฟล์ |
| Dashboard | Flask | แสดงสถานะสด + หน้าตั้งค่าโซน |
| Log | CSV + SQLite | event log ต่อโซน |

### ทำไมใช้ YOLO แทน HOG/MediaPipe Pose

- **HOG** ตรวจคนนั่ง/มุมมองจากด้านบนไม่แม่นยำ (false positive บนของบนโต๊ะ)
- **MediaPipe Pose** ตรวจคนหลายคนในมุมบนได้ไม่ดี และหลอกผิดจากของบนโต๊ะเมื่อ crop
- **YOLO** ตรวจครั้งเดียวบนเต็มเฟรม แล้วแมป center เข้าโซน — ทั้งแม่นยำกว่าและเร็วกว่า

### กลยุทธ์การตรวจจับ (สำคัญ)

ตรวจจับบุคคล **1 ครั้งบนเต็มเฟรม** (downscale เป็น 480px) แล้วเช็คว่า center ของแต่ละคน
ตกใน ROI ของโซนใด — **ไม่ใช่** crop แยกตรวจต่อโซน (crop ทำให้เกิด false positive จากของบนโต๊ะ)

## 5. คำแนะนำการเลือกและติดตั้ง CCTV

| เรื่อง | แนะนำ |
|---|---|
| โปรโตคอล | RTSP / ONVIF (Hikvision, Dahua, UBNT, TP-Link) |
| ความละเอียด | 1080p ขึ้นไป |
| ตำแหน่ง | กล้องต่อ 1 โต๊ะ/โซน มุมสูงเล็กน้อย มองเห็นท่านั่ง + มือบนโต๊ะ |
| FPS | 2–5 fps พอสำหรับ occupancy (ประหยัดทรัพยากร) |
| แสง | แสงคงที่ หลีกเลี่ยงม่าน/หน้าต่างกระแทกแสงในกรอบ |
| Edge Box | mini PC / NVR รัน Docker: Python + OpenCV + ultralytics (CPU ได้) |
| Privacy | เปิด privacy masking บริเวณที่ไม่ใช่โซนโต๊ะ, ไม่บันทึกวิดีโอต่อเนื่อง |

## 7. การติดตั้งและรัน

### ติดตั้ง dependencies

```bash
python -m venv .venv
.venv/Scripts/activate          # Windows  (Linux/mac: source .venv/bin/activate)
pip install -r requirements.txt
```

ultralytics ลาก torch มาด้วย รวมแล้ว venv ~**1.1 GB** ครั้งแรกที่รันจะดาวน์โหลด
`yolov8n.pt` (6.5 MB) ให้อัตโนมัติ

### รันทดสอบ (วิดีโอตัวอย่าง)

```bash
cd cctv-desk-monitor
# threshold สั้นๆ สำหรับทดสอบกับวิดีโอตัวอย่าง
python desk_occupancy_multi.py --config occupancy.yaml --test-away 3
```

### รันกับ RTSP จริง

แก้ `occupancy.yaml` ส่วน `source` เป็น `rtsp://user:pass@IP:554/stream1` แล้ว:

```bash
python desk_occupancy_multi.py --config occupancy.yaml
```

### รันเทสต์

```bash
python test_pipeline.py     # 19 เคส - ใช้ detector ปลอม ไม่ต้องมี torch
```

### เปิด dashboard

เปิดเบราว์เซอร์ที่ <http://localhost:8080/>

### ตั้งค่าโซนโต๊ะ (ครั้งเดียว)

1. หน้า dashboard → กด **"ตั้งค่าโซนโต๊ะ"** หรือเข้า <http://localhost:8080/calibrate>
2. ระบบดึง snapshot จริงจากแต่ละกล้อง
3. **ลากกรอบ** บริเวณที่ตัวคน/เก้าอี้ปรากฏจริงในแต่ละกล้อง
4. กด **"บันทึก & ใช้งาน"** → โซนใหม่ใช้ทันที + บันทึกลง `data/zones_calibrated.json`
   (โหลดอัตโนมัติครั้งต่อไป)

## 8. Config (`occupancy.yaml`)

```yaml
cameras:
  - id: cam-1
    name: "Floor 3 - Zone A"
    source: rtsp://user:pass@10.0.0.5:554/stream1   # หรือไฟล์วิดีโอ
    fps: 2
    zones:
      - id: desk-1
        name: "Desk 1"
        roi: [0, 0, 960, 1080]     # x1,y1,x2,y2 ใน source pixels
        away_seconds: 60
      - id: desk-2
        name: "Desk 2"
        roi: [960, 0, 1920, 1080]
        away_seconds: 60

storage:
  log_csv: data/occupancy.csv
  db: data/occupancy.sqlite

dashboard:
  enabled: true
  host: "0.0.0.0"
  port: 8080

pose:
  model: models/pose_landmarker.task
  downscale_width: 480
  min_motion_area: 400
  presence_confidence: 0.5

# optional - ถ้าไม่ใส่ จะใช้ models/yolov8n.pt แล้ว fallback ไปให้ ultralytics
# ดาวน์โหลดเอง และใช้ค่า confidence จาก pose.presence_confidence
detector:
  yolo_model: models/yolov8n.pt
  confidence: 0.5
  torch_threads: 2     # สำคัญ! ดูข้อ 11 - ปล่อยให้ใช้ทุก core กิน CPU เพิ่ม 11 เท่าโดยไม่เร็วขึ้น
```

## 10. ผลการทดสอบความแม่นยำ

### สรุปรวม — ทุกโมเดลที่วัดแล้ว 20 รายการ (อ่านตารางนี้ก่อน)

เรียงจากเร็วไปช้า — นับ variant OpenVINO ของ yolo11n/11s เป็นรายการแยก

ทุกตัววัดด้วยชุดทดสอบเดียวกัน: **46 ภาพจาก COCO val2017 / คน 131 (ถูกจอบัง 69)**

> **วิธีอ่านคอลัมน์ความเร็ว:** ms เทียบข้ามรอบวัด**ไม่ได้** เพราะเป็นโน้ตบุ๊กที่
> throttle ตามความร้อน (yolo11n วัดได้ 110 / 129 / 141 ms ใน 3 รอบ) จึง normalize
> เป็น **"เท่าของ `yolo11s` ในรอบเดียวกัน"** แทน — ค่านี้เทียบข้ามรอบได้
> ส่วน **recall/FP เป็น deterministic** (รัน 2 รอบได้ตรงกันทุกแถว) จึงเทียบได้ตรงๆ

### เลือกตัวไหน

| ถ้าต้องการ | ใช้ |
|---|---|
| **deploy วันนี้ สมดุลสุด** | **`yolo11s` + OpenVINO** (ไม่เปลี่ยน) |
| เบาสุดที่ยังยอมรับได้ | `yolo11n` + OpenVINO |
| แม่นสุดโดยไม่สนความเร็ว | `dfine-m` (ถูกบัง 100%) |
| ตัวที่น่าลงทุนทดลองต่อ | `dfine-n` + OpenVINO/INT8 → ดูข้อ 14 |
| หลายสิบกล้องต่อ 1 edge box | `rtmdet-n-person` — แต่ต้องวัดกับกล้องจริงก่อน |
| ตัดทิ้งได้เลย | `rtmdet-tiny/s`, `crowdhuman-yolov8n`, `ssdlite`, `faster-rcnn` |

**บทเรียนที่ใช้ซ้ำได้ 3 ข้อจากตารางนี้:**

1. recall ของ "คนถูกบัง" *สูงกว่า* recall รวมในทุกโมเดล → **การถูกจอบังไม่ใช่จุดอ่อนหลัก**
   เคสที่พลาดจริงคือคนตัวเล็กไกลๆ ภาพเบลอ **การวางกล้องสำคัญกว่าการเลือกโมเดล**
2. อย่าตัดสินสถาปัตยกรรมจากรุ่นใหญ่สุดของมัน — `rtdetr-l` ทำให้สรุปผิดว่า
   "transformer ไม่คุ้ม" ทั้งที่ `dfine-n` ชนะมันทุกด้าน
3. โมเดลที่เทรนกับ **โดเมนอื่น** (กล้องมองลงมา) จะดูแย่บนชุดทดสอบ COCO ระดับสายตา
   เสมอ — ตัวเลขนั้นไม่ใช่หลักฐานว่ามันแย่ ต้องวัดซ้ำด้วยภาพจากกล้องจริง

รายละเอียดแต่ละรอบวัดอยู่ในหัวข้อย่อยถัดไป

### เปรียบเทียบโมเดล กับฉาก "คนถูกจอบัง" จริง (2026-09-15)

ชุดทดสอบ: **46 ภาพจาก COCO val2017 / คน 131 คน (ถูกจอบัง 69 คน)** — ground truth
เป็นของ COCO ไม่ใช่การนับเอง รายละเอียดการคัดภาพดู `benchmark/README.md`

| model | ขนาด | ms/เฟรม | recall ทุกคน | **recall คนถูกจอบัง** | false pos |
|---|---|---|---|---|---|
| yolov8n | 6.5 MB | ~55 | 75% | 81% | 1 |
| **yolo11n** ← ค่าเริ่มต้น | **5.6 MB** | **~68** | 76% | **88%** | 1 |
| **yolo11s** ← ตัวเลือกแม่นกว่า | 19.3 MB | **~120** | 85% | **94%** | 2 |
| yolov8s | 22.6 MB | ~120 | 85% | 93% | 2 |

ทั้ง `yolo11n` และ `yolo11s` ลงไว้ใน `models/` แล้ว **สลับได้ที่ `detector.yolo_model`
ใน `occupancy.yaml` บรรทัดเดียว** โดยไม่ต้องดาวน์โหลดอะไรเพิ่ม

| | yolo11n | yolo11s |
|---|---|---|
| recall คนถูกจอบัง | 88% (พลาด 12%) | 94% (พลาด 6%) |
| ms/เฟรม | ~68 | ~120 |
| edge 4-core @ 2fps | ~12-15 กล้อง | ~6-8 กล้อง |

**ข้อสังเกตสำคัญ:** recall ของ "คนถูกจอบัง" (88-94%) *สูงกว่า* recall รวมทุกคน (76-85%)
แปลว่า **การถูกจอบังไม่ใช่จุดอ่อนหลัก** — เคสที่พลาดจริงคือคนตัวเล็กไกลๆ ภาพเบลอ
และคนที่เห็นแค่แขน/มือในฝูงชน ดังนั้น **การวางกล้องให้คนอยู่ใหญ่พอในเฟรม
สำคัญกว่าการเลือกโมเดล**

> ข้อจำกัด: COCO เป็นภาพระดับสายตา ไม่ใช่มุม CCTV มองลงมา
> ลำดับอาจเปลี่ยนเมื่อติดกล้องจริง — รัน `benchmark/benchmark_models.py` ซ้ำด้วยภาพจากกล้องตัวเองได้

**สิ่งที่ได้จากรอบนี้ 4 ข้อ:**

1. **D-FINE ล้ม `rtdetr-l` ขาด** — `dfine-n` แม่นเท่า `rtdetr-l` (ถูกบัง 97% ทั้งคู่)
   แต่**เร็วกว่า 2.3 เท่า** และ recall รวมดีกว่า (92% vs 90%) ข้อสรุปเดิมที่ว่า
   transformer detector ไม่คุ้มจึงผิด — มันเป็นข้อจำกัดของ *รุ่น* ไม่ใช่ *สถาปัตยกรรม*
   `dfine-m` จับคนถูกบังได้ครบ **69/69 = 100%**

2. **แต่ยังไม่เปลี่ยน production** — `dfine-n` (434 ms) ยังช้ากว่า `yolo11s` (217 ms)
   สองเท่า และเป็น PyTorch ล้วน **ยังไม่ได้ export OpenVINO** ถ้าได้อัตราเร่งเท่าที่
   YOLO ได้ (1.7-2.6 เท่า) จะลงมา ~170-255 ms ที่ recall ถูกบัง 97%
   = **ชนะ `yolo11s` ทั้งสองด้าน** → เป็นการทดลองถัดไปที่คุ้มสุด (ข้อ 14)
   ข้อควรระวัง: FP ของ D-FINE สูงกว่า (4-7 vs 2) ซึ่งแปลว่า "PRESENT ตอนไม่มีคน"
   ต้องจูน `conf` ขึ้นก่อนใช้จริง

3. **RTMDet แพ้ขาด ตัดทิ้งได้** — `rtmdet-tiny` (265 ms/83%) ทั้งช้ากว่าและแม่นน้อยกว่า
   `yolo11n` (141 ms/88%) ส่วน `rtmdet-s` แพ้ `yolo11s` ทุกช่อง
   แต่ `rtmdet-n-person` ที่ **23.2 ms (เร็วกว่า `yolo11s` 9.4 เท่า) FP = 0**
   เข้าข่ายเดียวกับ OpenVINO person-detection ข้างล่าง — เทรนกับกล้องมองลงมา
   แต่ถูกทดสอบด้วยภาพ COCO ระดับสายตา **ต้องวัดซ้ำกับกล้องจริงก่อนตัดสิน**
   ที่ 23 ms มันเป็นตัวเดียวที่รันได้หลายสิบกล้องบน edge box ตัวเดียว

4. **CrowdHuman fine-tune ล้มเหลว — สมมติฐานผิด** คาดว่าน้ำหนักที่เทรนกับฉาก
   แออัด/ถูกบังจะชนะเรื่องคนถูกบัง ผลออกมาตรงข้าม (63%/75%) **แย่กว่า `yolov8n`
   เปล่าๆ ทุกช่อง** สาเหตุที่น่าจะเป็น: checkpoint เป็น `best.pt` จาก training run
   ของคนทั่วไปบน HF ไม่มีตัวเลขยืนยัน + เทรนคลาสเดียวบน dataset แคบจึงเสีย
   generality + **นิยามกล่องต่างกัน** (CrowdHuman ใช้ full-body รวมส่วนที่ถูกบัง
   COCO ใช้เฉพาะส่วนที่มองเห็น) ทำให้ center เลื่อนจาก GT
   ถ้าจะเอาแนวคิดนี้จริงต้อง fine-tune เองจาก dataset ต้นฉบับ ไม่ใช่หยิบจาก hub

รันตารางนี้ซ้ำสองรอบ **recall กับ FP ออกมาตรงกันทุกแถว** (deterministic)
ส่วน ms แกว่ง 3-20% ตามความร้อนของโน้ตบุ๊ก — ยืนยันอีกครั้งว่าให้เชื่อ
อัตราส่วนภายในรันเดียวกัน ไม่ใช่ค่าสัมบูรณ์

### รอบล่าสุด — รันจริงเต็ม pipeline (2026-09-15, Windows 11 / 12-core CPU)

ทดสอบกับ `data/sample_real.mp4` (สังเคราะห์จากภาพคนจริง 960x540, วนลูป 20 วิ)
โซนซ้ายจงใจวาง**จอคอมพิวเตอร์ไว้แต่ไม่มีคน** เพื่อจับ false positive แบบที่ HOG เคยพลาด

| โซน | ความเป็นจริง | ผลที่ได้ |
|---|---|---|
| desk-1 (ซ้าย — จอคอม ไม่มีคน) | ไม่มีคน | `AWAY`, `person_count=0` **ตลอด 60 วินาที** ✓ |
| desk-2 (ขวา — มีคนเป็นช่วง) | มีคน 7 วิ / ว่าง 13 วิ | `AWAY` → `PRESENT` → `AWAY` วนถูกตามจังหวะ ✓ |

- **false positive = 0** ไม่มี event ของ desk-1 เกิดขึ้นเลยแม้แต่ครั้งเดียว
- จุดเหลือง (person center) ตกบนลำตัวคนพอดี กรอบเขียว/แดงตรงตามสถานะ
- สถานะ `(PRESENT, person_count=0)` ที่เห็นช่วงสั้นๆ คือช่วง grace ของ `away_seconds` — ถูกต้องตาม design

> วิดีโอทดสอบเป็นภาพสังเคราะห์ ยัง**ไม่ได้**ทดสอบกับกล้อง CCTV จริงในออฟฟิศ

## 11. การใช้ทรัพยากร

วัดจริงบน Windows 11 / 12-core CPU (ไม่ใช้ GPU) — 1 กล้อง 2 โซน @ 2 fps, YOLOv8n @ 480px:

| ตัวชี้วัด | ค่า |
|---|---|
| inference | **~68 ms** (yolo11n) / **~120 ms** (yolo11s) |
| CPU | **29% ของ 1 core** (2.4% ของเครื่อง 12 core) |
| RAM | **~410 MB** (torch กินเป็นหลัก) |
| ดิสก์ | venv + torch ~**1.1 GB**, โมเดล 6.5 MB |

### ⚠️ กับดัก OpenMP busy-wait (เจอตอนวัดจริง)

ตอนแรกวัดได้ CPU **334% ของ 1 core** ทั้งที่ inference ใช้จริงแค่ ~9% (44ms × 2 เฟรม/วิ)
สาเหตุคือ OpenMP ของ torch ดีฟอลต์เป็น **busy-wait** — thread ที่ทำงานเสร็จจะวนรอเปล่าๆ
แทนที่จะหลับ ทำให้ CPU พุ่งทั้งที่ระบบแทบไม่ทำอะไร

แก้ในโค้ดแล้ว 2 จุด:

```python
os.environ.setdefault("OMP_WAIT_POLICY", "PASSIVE")   # ต้องตั้งก่อน import torch
torch.set_num_threads(2)                              # ปรับผ่าน detector.torch_threads
```

ผลวัดซ้ำหลังแก้: **334% → 29%** (ลดลง 11 เท่า)

เหตุผลที่จำกัดแค่ 2 threads ได้โดยไม่เสียความเร็ว — วัดแล้วเวลาต่อเฟรมแทบไม่ต่างกัน:

| torch threads | ms/เฟรม |
|---|---|
| 6 (default = ครึ่งหนึ่งของ core) | 43.8 |
| 4 | 48.5 |
| 2 (**ค่าที่ใช้**) | 47.1 |
| 1 | 51.4 |

### ประมาณการขนาดเครื่อง

| โมเดล | ms/เฟรม | ต่อกล้องที่ 2 fps | edge 4-core |
|---|---|---|---|
| `yolo11n` | ~68 | ~13.6% ของ 1 core | ~12-15 กล้อง |
| `yolo11s` | ~120 | ~24% ของ 1 core | ~6-8 กล้อง |

(จำนวนโซนต่อกล้องแทบไม่เพิ่มภาระ เพราะตรวจเต็มเฟรมครั้งเดียวแล้วค่อยแมปเข้า ROI) (จำนวนโซนต่อกล้องแทบไม่เพิ่มภาระ
เพราะตรวจเต็มเฟรมครั้งเดียวแล้วค่อยแมปเข้า ROI)

## 12. ข้อจำกัดที่ต้องรู้

- **"ไม่ขยับ" ≠ "ไม่ทำงาน"** ระบบวัด occupancy เท่านั้น ไม่ใช่ประสิทธิภาพ
- **แม่นยำขึ้นเมื่อ ROI แม่นยำ** ใช้หน้า calibrate ลากกรอบให้ตรงบริเวณตัวคน/เก้าอี้ ห้ามกว้างเกินไป
- **คนเดินผ่าน** อาจทำให้โซนเป็น `PRESENT` ชั่วคราว (ระบบรอ `away_seconds` ก่อนเปลี่ยน `AWAY`)
- **แสงน้อย/มุมบัง** อาจลดความแม่นยำ — ตั้งกล้องให้มองเห็นชัด
- **OpenCV 5.x ตัด `cv2.HOGDescriptor` ออกแล้ว** fallback ชั้นสุดท้ายจึงใช้ไม่ได้บน cv2 5.x
  ถ้าไม่มีทั้ง `ultralytics` และไฟล์ MediaPipe โปรแกรมจะหยุดพร้อมบอกวิธีแก้
  (แนะนำให้ติดตั้ง `ultralytics` อยู่แล้วเพราะแม่นสุด)
- **ชื่อโซนภาษาไทยบนวิดีโอ** ฟอนต์ Hershey ของ OpenCV วาดไทยไม่ได้ (ออกมาเป็น `????`)
  โค้ดจึงใช้ Pillow + ฟอนต์ไทยในเครื่อง (Leelawadee UI / Tahoma / Loma) วาดแทน
  ถ้าหาฟอนต์ไม่เจอจะถอยไปแสดง **zone id** (ASCII) แทนชื่อ — หน้า dashboard แสดงไทยได้ปกติเสมอ
- **อ่านไฟล์วิดีโอจะช้ากว่าเวลาจริง** worker อ่านเฟรมตาม `fps` ที่ตั้ง (เช่น 2) แต่ไฟล์อาจเป็น 10 fps
  เวลาทดสอบกับไฟล์ให้ตั้ง `fps` ให้ตรงกับไฟล์ ถ้าอยากให้เล่นเป็นเวลาจริง (กับ RTSP ไม่มีปัญหานี้)

- **เก็บให้น้อยที่สุด** วัดสถานะ occupancy ไม่ใช่จับใบหน้า/ระบุตัวบุคคล ไม่เก็บวิดีโอดิบ
- **ความปลอดภัยข้อมูล** เก็บ log ในเครือข่ายองค์กร จำกัดสิทธิ์ กำหนดอายุเก็บข้อมูล
- **ใช้เพื่อปรับปรุงงาน** ไม่ใช่ลงโทษอย่างเดียว

> **หมายเหตุ:** ส่วนนี้เป็นแนวทางทั่วไป ไม่ใช่คำแนะนำทางกฎหมาย
> ให้ฝ่ายกฎหมายขององค์กรตรวจสอบก่อนใช้งานจริง

## 14. แนวทางต่อยอด (ยังไม่ได้ทำ)

- ส่งแจ้งเตือนเข้า Line/Slack webhook เมื่อโซนเป็น `AWAY`
- รายงานสรุปรายวัน (เปอร์เซ็นต์ occupancy ต่อโซน/ต่อช่วงเวลา)
- export รายงานเป็น PDF/Excel
- รองรับ polygon ROI (ไม่ใช่แค่กรอบสี่เหลี่ยม)
- **export โมเดลเป็น OpenVINO / ONNX** — บน edge box ที่เป็น CPU Intel มักเร็วขึ้น 2-3 เท่า
  (`YOLO("yolo11n.pt").export(format="openvino")`) ยังไม่ได้ลองวัดในโปรเจกต์นี้
- **⭐ export `dfine-n` เป็น OpenVINO แล้ววัดซ้ำ** — การทดลองที่คุ้มสุดที่ค้างอยู่
  ตอนนี้มันแม่นกว่า `yolo11s` 3 จุด (ถูกบัง 97% vs 94%) แต่ช้ากว่า 2 เท่า
  ถ้า OpenVINO ให้อัตราเร่งเท่าที่ YOLO ได้ มันจะชนะทั้งสองด้าน
- **INT8 quantization ผ่าน NNCF** — ของฟรีก้อนต่อไปหลังจาก FP32 OpenVINO
  (`export(format="openvino", int8=True)`) ปกติได้อีก 2-3 เท่าบน CPU Intel
- **วัดซ้ำด้วยภาพจากกล้องที่ติดจริง** โดยเฉพาะ `rtmdet-n-person` (22 ms, FP=0)
  กับ OpenVINO person-detection — ทั้งคู่เทรนกับกล้องมองลงมา ชุดทดสอบ COCO
  ปัจจุบันลำเอียงต่อต้านมัน ถ้าผลกลับทิศจะรันได้หลายสิบกล้องต่อ edge box
- ถ้ากล้องจริงแล้วพบว่าพลาดคนนั่งมุมยาก: ลอง `yolo11s` หรือโมเดลที่เทรนกับ
  มุมกล้อง overhead/fisheye โดยเฉพาะ
- **ByteTrack** (`model.track()` ใน ultralytics) — ไม่เพิ่ม recall ของเฟรมเดี่ยว
  แต่ track ยัง alive ตอน detector พลาด จึงลด flicker ของ state machine ราคาถูกมาก
  หลีกเลี่ยง BoT-SORT + Re-ID เพราะเก็บ appearance embedding = ระบุตัวบุคคลได้
  ขัดกับ privacy-by-design ในข้อ 3
- **ROI classifier แทน whole-frame detector** — กล้อง fix + โซน fix + ต้องการแค่
  `PRESENT`/`AWAY` จริงๆ คือ binary classification บน crop เล็กๆ
  (MobileNetV3-small 96x96 ≈ 1-3 ms/โซน = ถูกกว่า detector 30-100 เท่า)
  ต้องเทรนต่อการติดตั้ง — ใช้ YOLO เป็น teacher เก็บ label อัตโนมัติสัปดาห์แรกได้
- เก็บภาพ snapshot ตอนเกิด event เพื่อ audit (พร้อม privacy masking)

## 15. ประวัติการพัฒนา (สำหรับ context ต่อยอด)

1. เริ่มจากเวอร์ชันเต็ม `ACTIVE`/`IDLE`/`AWAY` (MediaPipe Pose + motion) — ใช้ทรัพยากรเยอะ (~85% CPU/กล้อง)
2. ผู้ใช้บอก "แค่อยากรู้ว่าทำงานอยู่มั้ย" → ลดเป็น `PRESENT`/`AWAY` (presence-only) ประหยัด 3–4 เท่า
3. เพิ่ม multi-camera/multi-zone + dashboard
4. ผู้ใช้บอกผลไม่แม่นยำ → สลับจาก HOG → MediaPipe Pose → YOLOv8n (แม่นยำสุด)
5. แก้บั๊กสำคัญ: ส่ง `dict` แทน `bool` ทำให้ทุกโซนกลายเป็น `PRESENT` เสมอ
6. เปลี่ยนกลยุทธ์จาก crop-ต่อโซน → ตรวจเต็มเฟรมครั้งเดียวแล้วแมปเข้าโซน (ลด false positive)
7. ผู้ใช้บอก "workstation fix ตำแหน่งอยู่แล้ว" → เพิ่มหน้าตั้งค่าโซนแบบลากเส้นบน snapshot + persist
8. เขียน `desk_occupancy_multi.py` ใหม่ทั้งไฟล์จาก spec ในเอกสารนี้ (2026-09-15)
   ทดสอบ 18 เคสผ่านหมด: state machine, endpoints ทั้ง 8 ตัว, calibrate + persist,
   และเคสบั๊กเดิม (ส่ง `dict` แทน `bool` — ตอนนี้ `Zone.update()` โยน `TypeError` ทิ้งเลย)
9. ติดตั้ง YOLOv8n จริงแล้วรันกับวิดีโอที่มีคนจริง (2026-09-15) — ยืนยัน false positive = 0
   บนโซนที่มีจอคอมแต่ไม่มีคน, เจอและแก้ 2 เรื่องระหว่างทาง:
   **OpenMP busy-wait** (CPU 334% -> 29%) และ **ชื่อโซนไทยขึ้นเป็น ???? บนวิดีโอ** (ใช้ Pillow วาดแทน)
10. เปรียบเทียบ 4 โมเดล (2026-09-15) แล้วเปลี่ยนตัวหลักจาก `yolov8n` -> **`yolo11n`**
11. สร้างชุดทดสอบจริงจาก COCO val2017 (46 ภาพ/131 คน) เฉพาะฉากที่คนถูกจอบังจริง
    พร้อม `benchmark/benchmark_models.py` — ผลกลับทิศจากการวัดด้วย 2 ภาพก่อนหน้า:
    `yolo11s` ดีกว่า `yolo11n` จริง (94% vs 88%) จึงลงไว้ทั้งคู่ให้สลับได้ใน config
    ระหว่างทางเจอว่าตัวกรองแรกนับ "คนที่ปรากฏบนหน้าจอทีวี" เป็นคนถูกบัง ต้องใส่เพดาน 60%
12. ลองโมเดลนอกตระกูล YOLO (2026-09-15): rtdetr-l, faster-rcnn x2, ssdlite,
    และ OpenVINO Model Zoo (person-detection-retail-0013 / -0202)
    ไม่มีตัวไหนชนะ yolo11s ในแง่ speed/accuracy บนชุดทดสอบนี้
    แต่เจอของดี: **export เป็น OpenVINO เร็วขึ้น 1.7-2.6 เท่าโดยความแม่นแทบไม่ตก**
13. ขยาย `benchmark/benchmark_models.py` ให้รองรับ 3 backend (ultralytics /
    transformers / onnx+openvino) แล้ววัด **D-FINE, RTMDet, CrowdHuman** (2026-09-15)
    ผล: **`dfine-n` ล้ม `rtdetr-l` ขาด** (แม่นเท่ากันแต่เร็วกว่า 2.4 เท่า) จึงกลับ
    ข้อสรุปเดิมที่ว่า "transformer ไม่คุ้ม" — เดิมวัดแต่รุ่นใหญ่สุดของตระกูล
    RTMDet แพ้ขาดตัดทิ้ง, CrowdHuman checkpoint จาก hub แย่กว่า `yolov8n` เปล่าๆ
    (สมมติฐานผิด — น่าจะเพราะนิยามกล่อง full-body ต่างจาก COCO)
